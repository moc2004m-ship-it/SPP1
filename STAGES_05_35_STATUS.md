# Stages 05–35 status

This build is a real server-backed development build, not a fake production claim.

## Implemented in this build
- Stage 5: authentication foundation and security boundaries from previous build.
- Stages 6–16, 18–19, 23–24, 26, 29–31, 33–35: backend domain foundation plus a runnable mobile/web shell that calls the backend for profiles, rooms, events, follows/friends/blocks, chat message creation, room joins/seats/settings/moderation, battles/games records, wallet/gift/inventory/family/notifications/settings/moderation/support records.
- New `/platform/api/*` routes expose those server operations.
- New `/app` static route serves the mobile shell from the backend.
- The shell has Home, Rooms, Events and Profile navigation and uses live responses from the running backend process.
- Stage 17, 20–22, 25, 27–28, 32 are still not marked complete: their full business/game/payment/subscription engines require further implementation and/or external provider configuration.

## Important truthfulness boundary
The stage 6–35 domain store is still in-memory. It is a real server process and real API state, but it is not persistent production storage. Restarting the backend clears those domain records. No external payment, SMS, push, RTC or production cloud service is faked.

## Phase 3 update — see PHASE3_MOBILE_BACKEND_REPORT.md

## Phase 5 update — central systems (Account/ID → Wallet/Recharge → Inventory → Games → Gifts) — see PHASE5_CENTRAL_SYSTEMS_REPORT.md
Moved Wallet/Recharge, Inventory, Gifts and Games off the generic in-memory `feature_records` store onto four dedicated relational domains: new schema files `005_create_inventory.sql`–`008_create_game_matches.sql` (each with real foreign keys into `accounts`/`wallet_transactions` and UNIQUE/CHECK constraints enforcing idempotency), matching `InMemory*`/`Postgres*` repository pairs, and real orchestration services (`recharge.service.js`, `gifts.service.js`, `game-match.service.js`). Recharge now resolves coin amounts from a server-side package catalog and only credits a wallet after a real, fail-closed provider verification call (503 with no config — same pattern as the existing SMS/OAuth boundaries, never faked). Gifts now perform a real wallet debit at a server-side catalog price before any gift record is written; an insufficient balance blocks the record entirely. Game match creation is real and session-scoped; submitting a result stays explicitly blocked (403) because no per-game rules engine exists yet to determine a real winner — a fake/random/client-declared result was deliberately not substituted. 24 new dependency-free tests added (`inventory.repository.test.js`, `recharge.service.test.js`, `gifts.service.test.js`, `game-match.service.test.js`), all passing. Full backend suite re-run this session: 119 tests, 115 pass, 4 fail — same pre-existing `Cannot find module 'express'` cause as every prior phase (no network to `npm install`), confirmed by direct inspection, not a new regression. Postgres repositories for all four new domains are written and reviewed but not run against a live database — same boundary Wallet's Postgres path already had. No live/network testing was performed this session, per instruction.

## Stage 15 (Room Settings) completion — see STAGE15_FINAL_REPORT.md
Confirmed spec status going in: PARTIAL / NOT CLOSED. Inspection found `rooms.setting(roomId,key,value)` was a bare `store.add(15, ...)` stub — no ownership check, no key allowlist, no reuse of the create-time validators, and (critically) no actual effect on the stage-12 room record a client ever reads back; there was also no read side at all. Fixed this session: `rooms.setting(actorId, roomId, key, value)` now 404s for an unknown room, 403s for a non-owner (checked at the service level, not just the route), validates `key` against an explicit allowlist routed through the exact same validators/resolvers `rooms.create()` already uses (`room.model.js`/`room-catalog.js` — no duplicate logic), applies a real partial patch to the room via `store.update(12, ...)`, and still writes the stage-15 audit record (now correctly attributing `actorId`). `password` is special-cased exactly as at create time: only the hash is ever persisted, and the plaintext never reaches the audit record either. Added the symmetric read side, `rooms.getSettings(actorId, roomId)` (owner-only). Routes: fixed `POST /api/rooms/:roomId/settings`'s call signature and added `GET /api/rooms/:roomId/settings`, both behind the existing, already-tested `requireRoomOwner`. 20 new tests added (`rooms.stage15.settings.test.js`, 16/16 pass; `platform.room-settings.stage15.routes-contract.test.js`, 4/4 pass). Full suites after this change: Backend 848 tests / 844 pass / 4 fail (the same four pre-existing environmental `Cannot find module 'express'` fails — zero new regressions; one of four repeated runs also showed the pre-existing, already-documented `notifications` ordering timing flake from the Stage 6 report, confirmed unrelated by running that file alone 5x with 8/8 pass each time); Mobile 40/40 pass, unchanged (no Mobile file touched — Stage 15 has no Mobile UI, consistent with Stages 13/14/16). Remaining limitations are the same two permanent, already-documented environmental ones (no live Postgres, no live Express/HTTP server) — not new to this stage. Stage 15 is complete to the standard every other stage in this document is held to — not a claim of more than that.
